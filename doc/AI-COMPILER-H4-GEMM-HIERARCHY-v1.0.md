# H4 GEMM memory-hierarchy implementation v1.0

H4 extends the admitted scalar F32 GEMM path using [H2 facts](AI-COMPILER-H2-OWNED-MOVEMENT-FACTS-v1.0.md), [H3 costing](AI-COMPILER-H3-MOVEMENT-COSTING-v1.0.md) and immutable H20 device/resource/execution/budget profiles. The original v1.0 roadmap called GEMM H5; v1.3/v1.4 and the current workstream call it H4. This specification uses the current name without rewriting historical milestones.

The main addition is B operand retention across each thread's output rows. Existing persistent accumulators, A reuse across output columns, cooperative shared transport, compact/XOR or padded shared layouts and exact two-slot TMA remain in their owning materializers. H4 chooses among those existing mechanisms and two new staged scalar-retention siblings. It does not implement an MMA dtype change, new hardware instruction, deeper TMA pipeline, persistent CTA scheduling, packing or a general canonical-LNO GEMM route.

## Admission and scope

`-O3 -DSL:gemm_hierarchy=on` is an explicit opt-in. It additionally requires joint GEMM search, native CUDA WHIRL output, H20 96/141 admission, an imported pinned H3 supplement and owned H2 A/B layout/unique-alias/reuse/lifetime facts. Independently generated legacy CUDA output is excluded from H4 selection; the selected WHIRL image is authoritative. Missing prerequisites retain the existing admitted planner and fallback. O0/O1/O2 do not run H4. Scope is one active PU/site, never an IPA traversal. Existing F32 numerical and source/shape/effect permissions remain mandatory.

The new runtime-only fetch flag `DSL_FETCH_PLAN_FLAG_RETAIN_B` changes no mapped-image row or runtime ABI. An owning control enables at most S1R and T2R after the historical S1/D/T2 catalog. Direct demand remains the unchanged fallback. Retention requires TM>1 and 1<=TN<=32, a complete resource ledger and a supported staged transport. Unsupported layouts/TMA tails still refuse through existing admission.

## Detached work and resource model

For one CTA, let P=ceil(K/BK)*BK and T=(BM/TM)*(BN/TN). Existing A hoisting loads T*TM*P shared F32 values. The original B consumer loads T*TM*TN*P values; retained B loads T*TN*P. Thus B shared reads fall by TM when the same ownership map is compared. Shared-copy writes are (BM+BN)*P F32 values and ordered compute remains 2*BM*BN*P scalar operations. These are padded execution/request envelopes, not actual inactive global loads or modified H2 source ledgers. Ragged cooperative copies retain their guards and shared zero fill.

Both baseline and retained staged candidates use this same H4 count adapter. H3 pays shared reads/writes and associated issue work separately from global transport and arithmetic. No global request reduction is invented for shared B retention. Direct candidates retain their existing sector/work projection. H2 useful/source bytes, cache assumptions and actual-spill unknowns stay unchanged.

The retained recipe conservatively adds TN F32 register reservations beyond the existing consumer envelope. Imported rounded RF allocation, shared allocation, visible SMs, CTA limits, coverage and finite queues can make it lose despite fewer loads. This reservation is not an actual ptxas register count or spill-free proof. H3's explicit spill scenario remains required. Physical inputs and lower/upper scenarios remain estimates; no new overlap discount or bandwidth multiplier is introduced.

## Two-phase selection and fixed application

The complete joint catalog is bounded by 96 records (at most the historical 16 tiles times five recipes). H3 site/request estimate, proposal, detached-memory and cooperative deadline limits are shared with other strategies/PUs. The reserved 8 MiB transient-work allowance and deadline are checked before expanding the H4 catalog; insufficient work allowance leaves the historical catalog in place. Missing or budget-incomplete comparison retains the historical winner; new retained siblings never enter legacy cycle profitability. Ordinal ties remain deterministic. Candidate exploration constructs no WN/ST/TY or device PU and performs no probing, compilation, reference execution, timing or profiling. Actual source facts are captured before exploration and freshly compared before application; native symbol/type counts are also checked around search.

The winner is reconstructed once in the existing disposable fetch analysis. Fresh H2 source and H3 model/profile/budget, geometry/layout/consumer identity and ns score are validated before staging. At the driver handoff the copied source proof, current device/model and fixed recipe/score are revalidated without restoring or traversing the completed source PU. Only that fixed winner enters device-WHIRL construction; revalidation performs no alternative search and spends no new search budget. Failed source/model/specification/resource checks preserve existing refusal/fallback behavior and publish no valid partial CUDA image.

The selected materializer prefixes each q step with TN loads into explicit scalar F32 symbols, then reuses those symbols across the existing ascending i/output folds. The j updates are statically expanded so a private indexed B array cannot masquerade as register retention. Each output retains ascending K multiply/add operations and the existing accumulator lifetime. Source aliases/effects must already be ruled out before hoisting. Shared publication, TMA wait, all-consumer release, refill and drain remain unchanged. Device construction occurs in the driver-owned fresh PU, so no active source analysis is reused after mutation; existing source-lowering invalidation/publication stays in its owner.

## Explanations and validation

The selected owner builds a WHIRL COMMENT describing dimensions, ownership, persistent accumulation, retained or original B consumer, shared/TMA stage order, numerical policy, selected model and estimated cost. `whirl2c` prints that node without selecting an algorithm. The PREOPT COMMENT workaround remains unchanged. Distinct `-ft` paths protect source-interleaved native `.T` evidence during CUDA emission.

Qualification uses the actual pure production counter with an independently enumerated load/arithmetic oracle and malformed/overflow cases; native resource/ranking and source-isolation checks; both H20 identities; baseline/retained shared and TMA realizations, ragged edges and multiple slot generations; real WHIRL-derived host execution against ordered references; finite-budget, O-level, missing-proof/model, register-pressure, stale handoff and unchanged-default fallback checks. The optional `-DSL:gemm_hierarchy_checkpoint=PREFIX` retains immediate `PREFIX.pu-N.before.B` and `.after.B` around the selected retention transform in the same fresh device PU, using the existing isolated child-writer protocol. Genuine before/after `.B`, independent `-st -src` `.T`, complete raw diffs, original source inventory and producer/option hashes are retained immutably. GPU race checking, actual resource allocation, timing/profiling and model calibration remain H0/H7; no speedup or global-optimum claim follows from host checks.

Primary owner, successor, independent reviewer and approving lead remain TBD. AOT serving selection and OpenCTI remain deferred. Later GEMM slices may extend reviewed tile/depth/compute recipes under their own legality, model and materialization contracts.

Downstream CUDA/PTX compilation may already recover some operand reuse. The counted reduction describes the selected WHIRL/CUDA recipe before later optimization, not a measured reduction in hardware loads. Final ISA inspection, actual register/spill reporting and separate H20 measurements must establish the realized benefit.
