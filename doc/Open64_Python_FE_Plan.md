# Open64 Python Frontend Coding Plan

## Source Basis

This plan is based on the Python frontend architecture in
`imported_docs/DSC_Master_Design_Doc_v0.9_chapter_7.md`, the current DSL IR work
in `osprey/common/com`, and the new standalone `torch2whirl` frontend direction.

The near-term goal is to add a Python ingestion path that can create very
high-level WHIRL, while keeping the compiler middle end independent from Python.
The practical development goal is now dual OS: `torch2whirl` should build and
run on macOS for fast local iteration and inside the existing Linux Docker
environment for native Linux validation.

## Design Rules

1. Python is a source-language frontend and ingestion layer only.
2. `torch2whirl` is a standalone executable under `osprey/torch2whirl`, organized
   like other Open64 frontend directories such as `clang2whirl`.
3. The first milestone uses a two-step artifact boundary:
   `torch2whirl` creates a binary WHIRL file, then `opencc -x whirl` consumes it.
4. Ingestion emits first-class DSL/common operators, not intrinsic placeholders.
5. C++ owns WHIRL table construction, tensor descriptors, symbol/type creation,
   mapped image finalization, and binary IR compatibility.
6. `torch2whirl` must not depend on backend internals such as `osprey/be/cg`.
   The bridge should remain isolated from target code generation.
7. `torch2whirl` may use a modern C++ standard, starting with C++17, while
   following the plain Open64 coding style used around `osprey/be/opt`.
8. Opcode attributes are static operation parameters.
9. TensorDescriptorIR carries semantic tensor value state.
10. Compiler metadata carries source context, diagnostics, pass ownership,
    lowering hints, and profiling data.
11. A gatekeeper verifier must run before lowering so malformed high-level WHIRL
    does not silently enter downstream passes.

## Target Architecture

```text
Python model / DSL
  -> torch.export / FX / DSC capture graph
  -> open64_dsc.WhirlExportInterpreter
  -> open64_dsc._whirl native extension
  -> frontend-only WHIRL builder boundary
  -> torch2whirl binary very-high-level WHIRL artifact
  -> opencc -x whirl
```

The Python package coordinates model capture and graph traversal. The native
builder performs all WHIRL-specific construction. `torch2whirl` is the command
line boundary that makes this workflow reproducible without embedding Python in
the Open64 middle end.

## Dual OS Build Goal

The build strategy should make `torch2whirl` pleasant to develop before the full
compiler path is ready.

Pragmatic requirements:

1. `osprey/torch2whirl/Makefile.gbase` should work as a standalone makefile for
   quick local iteration.
2. `osprey/targdir/torch2whirl/Makefile.in` should be generated by configure so
   the executable remains under the Open64 build tree umbrella.
3. `configure --enable-torch2whirl-only` should create only the build files
   needed for the portable frontend scaffold, avoiding unrelated full-tree
   frontend requirements such as `CLANG_HOME`.
4. macOS should build with the platform C++ compiler and C++17.
5. The existing Linux Docker image should build and run the same executable as
   Linux native software.
6. The smoke test should cover `--help`, `--version`, and the current conversion
   placeholder path.
7. The build should stay independent from backend code generation libraries and
   headers.

Current observed validation:

```text
macOS:
  configure --enable-torch2whirl-only
  make -C osprey/targdir/torch2whirl clean all
  torch2whirl --help
  torch2whirl --version
  torch2whirl -o out.whirl model.py

Linux Docker:
  docker run ... /src/configure --enable-torch2whirl-only
  docker run ... make clean all
  docker run ... ./torch2whirl --help
  docker run ... ./torch2whirl --version
  docker run ... ./torch2whirl -o out.whirl model.py
```

Expected current behavior:

1. `--help` exits 0 and prints usage.
2. `--version` exits 0 and prints `torch2whirl 0.1`.
3. `-o out.whirl model.py` reaches the placeholder and exits 1 until real
   conversion is implemented.

This is useful even before WHIRL emission exists: it proves the frontend can be
built, launched, and tested on both development platforms without waiting for a
complete Open64 build.

## Phase 0: Preconditions

Before starting the Python package, stabilize the native DSL substrate enough
that Python has something concrete to target.

Required checks:

1. Current DSL/common infrastructure is reviewed and merged or otherwise stable
   enough for follow-up work.
2. Tensor type core and tensor descriptor storage rules are documented.
3. Common substrate operators needed by the first vertical slice are named and
   versioned.
4. `ir_b2a -st` can expose the DSL tensor/type/operator information needed for
   validation.
5. The native tests for `common.add`, `common.matmul`, tensor constants, and
   tensor type printing are passing.
6. The `torch2whirl` executable scaffold builds and runs on macOS and Linux
   Docker.

## Phase 1: Standalone torch2whirl Scaffold

Create `osprey/torch2whirl` as the frontend command directory. Keep it buildable
before it links to the native builder.

Initial files:

1. `osprey/torch2whirl/Makefile.gbase`
2. `osprey/torch2whirl/torch2whirl.cxx`
3. `osprey/torch2whirl/torch2whirl_driver.h`
4. `osprey/torch2whirl/torch2whirl_driver.cxx`
5. `osprey/torch2whirl/README.md`
6. `osprey/targdir/torch2whirl/Makefile.in`

Build-tree hooks:

1. Add `osprey/targdir/torch2whirl/Makefile` to configure generation.
2. Add `--enable-torch2whirl-only` for lightweight frontend-only setup.
3. Add a top-level `torch2whirl` make target.
4. Keep the makefile portable: `CXX`, `CPPFLAGS`, `CXXFLAGS`, `LDFLAGS`,
   `PREFIX`, and `BINDIR` should be overridable.

This phase is intentionally humble. A command-line shell that parses arguments,
prints help/version, and returns a clear "not implemented yet" error is already
valuable because it creates the cross-platform build/test surface.

## Phase 2: Native C++ Builder Layer

Add a narrow native builder API after the executable boundary is stable. This
avoids putting WHIRL table details inside Python and keeps the implementation
compatible with existing Open64 storage rules.

Candidate files:

1. `osprey/common/com/dsl_builder.h`
2. `osprey/common/com/dsl_builder.cxx`

Current builder concepts:

```c++
DSL_BUILDER_VALUE
DSL_BUILDER_OPERATOR
DSL_BUILDER_TENSOR_TYPE_CORE
DSL_BUILDER_TENSOR_DESCRIPTOR
DSL_BUILDER_OPERATOR_ATTRIBUTE
DSL_BUILDER_COMPILER_METADATA
DSL_BUILDER_MAPPED_IMAGE_REQUEST
```

Current staged APIs:

```c++
TY_IDX DSL_Builder_Create_Tensor_Type_Core(
    const char *name,
    TY_IDX element_ty,
    const DSL_BUILDER_TENSOR_TYPE_CORE *type_core);

BOOL DSL_Builder_Attach_Tensor_Descriptor(
    TY_IDX ty,
    const DSL_BUILDER_TENSOR_DESCRIPTOR *descriptor);

ST_IDX DSL_Builder_Create_Symbol(
    const char *name,
    TY_IDX ty,
    ST_CLASS sym_class,
    ST_SCLASS storage_class,
    ST_EXPORT export_class);

DSL_BUILDER_OPERATOR DSL_Builder_Create_Operator(
    DSL_OPCODE_ID opcode_id,
    UINT16 version,
    DSL_BUILDER_VALUE *kids,
    UINT32 kid_count,
    const DSL_BUILDER_OPERATOR_ATTRIBUTE *attrs,
    UINT32 attr_count);

BOOL DSL_Builder_Attach_Contract(
    DSL_BUILDER_OPERATOR wn,
    DSL_CONTRACT_ID contract_id);

BOOL DSL_Builder_Attach_Metadata(
    ST_IDX st,
    const DSL_BUILDER_COMPILER_METADATA *metadata,
    UINT32 metadata_count);

BOOL DSL_Builder_Finalize_Mapped_Image(
    const DSL_BUILDER_MAPPED_IMAGE_REQUEST *request);
```

The boundary should remain narrow: Python-facing bindings pass values,
attributes, metadata, and opaque Open64 handles; C++ creates real WHIRL objects
and owns symbol/type table mutation.

## Phase 3: Native Builder Regression Tests

Add tests under `osprey/common/com/tests` before binding Python.

Initial tests:

1. Create rank-2 integer tensor type and print it through the standard WHIRL
   print path.
2. Create tensor constants for zero and one.
3. Create `common.add` with `kid0` and `kid1` tensor operands.
4. Create `common.matmul` with tensor-one operands.
5. Create a small ResNet-like fragment with convolution, residual add, layout,
   and output metadata.
6. Verify static operation parameters remain opcode attributes.
7. Verify source context and lowering hints remain compiler metadata.
8. Verify tensor shape, dtype, layout, sharding, placement, and memory traits
   are reachable through TensorDescriptorIR accessors.
9. Verify the staged builder contract directly:
   tensor type/descriptor attachment, symbol metadata, operator payload
   formatting, invalid inputs, and the current mapped-image finalizer stub.
10. Verify `ir_b2a -st` emits WHIRL text plus symbol-table text for a native
    binary WHIRL artifact.

The tests should produce trace output when useful so `ir_b2a` behavior remains
visible during review.

Current Phase 3 fixtures:

1. `dsl_builder_contract_test.cxx` exercises the narrow native builder API
   without introducing Python bindings or backend lowering dependencies.
2. `dsl_common_add_print_test.cxx` and `dsl_common_matmul_print_test.cxx`
   continue to cover native common substrate operator printing.
3. `dsl_native_syntax_test.sh` syntax-checks the builder implementation and the
   Phase 3 test fixtures in a cheap Linux Docker loop.
4. `dsl_ir_tools_smoke_test.sh` validates `ir_b2a` and `ir_b2a -st` behavior
   once `opencc`, `ir_b2a`, and `ir_a2b` are built in the worktree.

## Phase 4: Binary WHIRL Artifact Boundary

Use the existing Open64 mapped-image machinery rather than inventing a new file
format.

Work items:

1. Finalize a minimal binary WHIRL artifact from the native builder.
2. Preserve compatibility with existing ELF WHIRL section rules.
3. Keep reserved DSL/tensor sections compatible with the current
   `elf_whirl.h` reservation strategy.
4. Ensure `ir_b2a -st` can dump the relevant tables for review.
5. Add round-trip tests where feasible:
   binary WHIRL -> `ir_b2a -st` -> inspected textual dump.

The first implementation can be conservative. The important requirement is that
the artifact is owned by Open64 infrastructure and survives outside Python.

Current Phase 4 status:

1. `DSL_Builder_Finalize_Mapped_Image` now rejects invalid requests and uses the
   existing `Open_Output_Info` / `Write_Global_Info` / `Close_Output_Info`
   writer path for the current global tables.
2. The first artifact slice writes global WHIRL sections with no PU tree. This
   proves the builder exits through the mapped-image/ELF WHIRL machinery while
   keeping function-body construction as the next API step.
3. `dsl_builder_contract_test.cxx` checks invalid finalizer requests and the
   minimal valid output-file creation path.

planned `_whirl.so` API.

## Phase 6: Native Binding Layer

Expose the C++ builder through `open64_dsc._whirl`.

Binding rules:

1. Python receives opaque handles, not full WHIRL objects.
2. Python does not allocate or mutate Open64 tables directly.
3. All symbol, type, descriptor, operator, and finalization calls funnel through
   the native builder.
4. Errors should be surfaced as Python exceptions with enough source context to
   debug bad ingestion.

The binding mechanism can be selected later. A C API plus a thin Python binding
is the safest compatibility shape; pybind11 is convenient if the build system
cost is acceptable.

## Phase 7: WhirlExportInterpreter

Implement the interpreter as a graph traversal layer over `torch.export` or FX.

First vertical slice operators:

1. `cnn.conv2d`
2. `cnn.batch_norm_infer`
3. `common.relu`
4. `cnn.max_pool2d`
5. `common.residual_add`
6. `cnn.global_avg_pool2d`
7. `common.flatten`
8. `common.linear`
9. `common.output_logits`

Mapping rules:

1. Static op parameters such as kernel shape, stride, padding, dilation, and
   groups become opcode attributes.
2. Tensor semantic state such as dtype, rank, logical shape, layout, sharding,
   placement, memory, quantization, and runtime state becomes TensorDescriptorIR.
3. Source layer names, debug spans, ownership notes, lowering hints, and profile
   data become compiler metadata.
4. Unsupported Python graph nodes must fail loudly with source context.

## Phase 8: torch2whirl Driver Integration

Grow the scaffold into the real frontend driver before integrating with
`opencc`.

Target command:

```sh
torch2whirl model.py --entry forward --sample-input shape:1,3,224,224 -o model.B
```

Validation commands:

```sh
ir_b2a -st model.B
opencc -x whirl model.B
```

The combined driver path can come later, after the standalone artifact path is
stable:

```sh
opencc -frontend=torch2whirl model.py ...
```

The combined mode must remain a convenience wrapper around the same artifact
boundary. It should not become an in-memory bypass around binary WHIRL
finalization, `ir_b2a` visibility, TensorDescriptorIR persistence, or gatekeeper
validation.

## Phase 9: Gatekeeper Verifier

The gatekeeper validates very-high-level WHIRL before lowering.

Initial checks:

1. Every tensor-producing operator has a complete TensorDescriptorIR.
2. Every operator has a valid domain and opcode.
3. Operator operands satisfy rank, dtype, layout, and domain compatibility
   contracts.
4. `common.add` and `common.residual_add` operands agree on broadcast or exact
   shape rules.
5. `common.matmul` operands satisfy matrix compatibility rules.
6. CNN operators have required static attributes such as kernel, stride,
   padding, dilation, and groups.
7. Metadata keys are not used to smuggle tensor semantic state.
8. Attribute keys are not used for source-only compiler context.

## Phase 10: OpenXLA Cross-Check Track

The Chapter 7 design uses PyTorch / OpenXLA as a reference shape. The local
coding plan should borrow the engineering pattern, not the StableHLO op set.

Expected lessons to import:

1. Keep Python graph capture as a thin coordinator.
2. Put compiler-owned object creation behind a compiled extension.
3. Maintain an explicit serialized artifact boundary.
4. Test graph capture, op mapping, metadata propagation, artifact printing, and
   unsupported-op failures separately.
5. Use small model fragments as conformance tests before full networks.
6. Keep backend-specific lowering out of the ingestion layer.
7. Keep platform smoke tests cheap enough that frontend changes can be tested
   without a full compiler build.

Relevant test patterns to adapt:

1. Small graph fragments before full models.
2. Golden text or structured dumps for captured graph/operator mapping.
3. Negative tests for unsupported graph nodes.
4. Metadata/source-context propagation tests.
5. Serialization boundary tests that prove the artifact can be inspected without
   re-running Python.
6. CLI tests that verify help/version/error behavior on every supported
   development platform.

## Milestones

1. M0: Standalone `torch2whirl` scaffold builds and runs on macOS and Linux
   Docker.
2. M1: Native builder creates and prints tensor `common.add`.
3. M2: Native builder creates and prints tensor `common.matmul`.
4. M3: Native builder creates a small ResNet-like graph fragment.
5. M4: Binary WHIRL artifact is produced and visible through `ir_b2a -st`.
6. M5: Python package skeleton calls a mock backend with the same API shape as
   the native extension.
7. M6: Python binding calls the native builder for tensor types, constants,
   symbols, and operators.
8. M7: `torch.export` or FX ingestion emits the first ResNet vertical slice.
9. M8: `opencc -x whirl` consumes the generated artifact without requiring
   Python in the middle end.

## Anti-Goals

1. Do not put Python into the compiler middle end.
2. Do not use intrinsics as the primary representation of high-level DSL
   operators.
3. Do not add speculative frontend hooks to unrelated ingestion paths.
4. Do not require the combined `opencc` driver path before the standalone
   `torch2whirl` path works.
5. Do not create a new binary IR format before exhausting the existing Open64
   mapped-image and ELF WHIRL mechanisms.
6. Do not make metadata or free-form key/value tables the fast path for tensor
   operand compatibility checks.
7. Do not link the language frontend bridge against backend/cg implementation
   details.

## Immediate Active Queue

1. Keep `torch2whirl` buildable through both direct source make and configured
   build-tree make.
2. Preserve and document the macOS plus Linux Docker smoke-test loop.
3. Keep the native builder API narrow: Python-facing code passes values,
   attributes, metadata, and opaque Open64 handles while C++ owns WHIRL/table
   mutation.
4. Keep the Phase 3 native syntax harness passing for builder, `common.add`,
   and `common.matmul` changes.
5. Build `opencc`, `ir_b2a`, and `ir_a2b` in a full Open64 build tree when
   available, then run `dsl_ir_tools_smoke_test.sh` to validate the inspection
   path.
6. Start Phase 4 by replacing the mapped-image finalizer stub with the smallest
   Open64-owned binary WHIRL artifact path.
7. Add the Python package skeleton only after the Phase 4 artifact boundary can
   produce an inspectable binary file.

## Practical Developer Loop

Use this loop while `torch2whirl` is still frontend-only:

```sh
/path/to/open64/configure --enable-torch2whirl-only
make -C osprey/targdir/torch2whirl clean all
./osprey/targdir/torch2whirl/torch2whirl --help
./osprey/targdir/torch2whirl/torch2whirl --version
./osprey/targdir/torch2whirl/torch2whirl -o out.whirl model.py
```

Use the Docker equivalent before treating a scaffold change as portable:

```sh
docker run --rm -v /path/to/open64:/src -v /private/tmp/open64-torch2whirl-linux:/build -w /build open64:x86_64-apple-silicon /src/configure --enable-torch2whirl-only
docker run --rm -v /path/to/open64:/src -v /private/tmp/open64-torch2whirl-linux:/build -w /build/osprey/targdir/torch2whirl open64:x86_64-apple-silicon make clean all
docker run --rm -v /private/tmp/open64-torch2whirl-linux:/build -w /build/osprey/targdir/torch2whirl open64:x86_64-apple-silicon ./torch2whirl --help
docker run --rm -v /private/tmp/open64-torch2whirl-linux:/build -w /build/osprey/targdir/torch2whirl open64:x86_64-apple-silicon ./torch2whirl --version
docker run --rm -v /private/tmp/open64-torch2whirl-linux:/build -w /build/osprey/targdir/torch2whirl open64:x86_64-apple-silicon ./torch2whirl -o out.whirl model.py
```

Before finishing frontend changes, scan for accidental backend coupling:

```sh
rg -n "be/cg|BE_CG|ercg|erauxdesc|#include .*be/" \
  -g '*.cxx' -g '*.h' -g 'Makefile*' \
  osprey/torch2whirl osprey/targdir/torch2whirl
```

Use the native builder syntax loop while Phase 2/3 code is moving:

```sh
docker run --rm -v /path/to/open64:/src -w /src open64:x86_64-apple-silicon \
  bash osprey/common/com/tests/dsl_native_syntax_test.sh
```

The native syntax script intentionally skips direct macOS execution unless
`OPEN64_DSL_TEST_ALLOW_DARWIN=1` is set, because the current common/com headers
still depend on GNU libstdc++ extensions such as `<ext/slist>`.
